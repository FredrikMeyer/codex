# Passkey rollout plan

Goal: let users connect devices using passkeys while keeping existing sessions and offline logging working. Assume recovery codes as a fallback until a recovery method is chosen.

## Design constraints

- WebAuthn runs at the frontend origin. The production PWA is at `https://fredrikmeyer.net/codex/`, and the API is at `https://asthma.fredrikmeyer.net`. Use `https://fredrikmeyer.net` as the expected frontend origin and plan for `fredrikmeyer.net` as the relying-party ID; the `/codex/` path is not part of either value. Verify production CORS allows this origin and configure local development separately. A later domain change affects existing passkeys.
- Events are associated with the existing six-character code. Keep that association during migration; use a stable opaque account identifier for WebAuthn user handles, not the secret code.
- SQLite is the production credential store. Preserve existing bearer tokens and local data; passkey authentication issues an additional independently stored token using the existing hashed-token model.
- Authentication and registration need a network connection. Existing local logging remains available offline. Do not erase a token or local data when offline.

## Ordered work

1. **Settle recovery and origins.** Decide whether to use saved one-time recovery codes, another passkey, email, or a combination; define lost-device and lost-recovery outcomes. Confirm local development origins and supported installed-PWA devices. Establish a strategy for any future frontend domain move.
2. **Define the account and credential model (started).** SQLite creates separate tables for opaque account handles and multiple credential records; handle creation is stable across restarts and workers. Credential storage includes metadata used by `py_webauthn`, with duplicate-ID protection and conditional signature-counter updates. The additive metadata upgrade is repeatable; complete a broader versioned migration strategy and add recovery records if selected. Determine JSON-only development behavior explicitly. No login or registration flow uses these tables yet.
3. **Implement the backend ceremony (started).** SQLite supports five-minute, single-use challenges shared across workers, with registration bound to an account. Registration and login endpoints use `py_webauthn` and require user verification; successful login issues a new token. Production defaults to RP ID `fredrikmeyer.net` and origin `https://fredrikmeyer.net`; local development can set `WEBAUTHN_RP_ID=localhost` and `WEBAUTHN_ORIGIN` to its exact frontend origin. SQLite is required. Complete browser and device testing, CORS verification, and the recovery design before rollout. Handle concurrent requests and sign counters according to the library and authenticator behavior. Counter updates alone do not prevent replay, especially for authenticators that always report zero. Rate-limit endpoints and avoid logging credentials or challenges.
4. **Connect sign-in to existing sessions.** After successful passkey verification, issue a new random bearer token stored as a hash, without invalidating other devices. Preserve existing API authorization and startup/offline behavior. Implement recovery and individual credential/session removal with appropriate confirmation and tests.
5. **Add PWA flows (started).** Connected users can register a passkey, and the setup screen can sign in with one. Browser integration covers registration and sign-in with a virtual authenticator; production CORS preflight allows `https://fredrikmeyer.net`. Add management of multiple passkeys and the chosen recovery flow, and test installed PWAs on actual devices. Handle unsupported platforms, cancellation and offline errors without clearing local data. Update the service-worker cache version when changing frontend assets.
6. **Test before rollout.** Cover successful ceremonies, wrong origin/RP, expired or replayed challenges, wrong account, concurrent workers, recovery, existing bearer sessions, cross-account isolation, and restart. Exercise passkey creation and login in browser automation with a virtual authenticator, then test the installed PWA on actual iOS and Android devices and across devices. Rehearse schema migration and rollback on copies of production data.
7. **Roll out alongside the current code.** Deploy backend compatibility first, then frontend. Allow each existing user to register and verify a passkey and recovery method from an authenticated device. Keep existing sessions valid and monitor errors without sensitive data. The six-character code remains a way to obtain a token during this phase, so passkeys do not eliminate that exposure yet.
8. **Retire code-based access deliberately.** Once each account has a verified alternative and a recovery path, disable code exchange for that account, including legacy `/login`, `/generate-token`, and code-retrieval flows as appropriate. Plan for inactive users before any global cutoff. Retain the code as an internal data association until a separate account-ID migration is justified.

Do not restore an old database backup over newer events, credentials, or tokens. A rollback must preserve current SQLite data and use an application version that understands the active schema and sessions.
